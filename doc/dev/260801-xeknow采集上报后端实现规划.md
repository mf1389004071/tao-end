## 2. 「联合登录」深入分析：为什么不用新缺号表、也不用 oauth_user

### 2.1 项目里和「第三方账号」相关的表

| 表 | 出处 | 本质 |
| --- | --- | --- |
| `oauth_user` | `changelog-2-auth.xml` | **联合/第三方登录**：用户用 GitHub/微信等 OAuth 登录本站时，存 `uuid/source/access_token/open_id/union_id`，且 **`user_id` 非空**（必须已有本平台用户） |
| `xiaoe_user_mapping` | business-022 | **业务侧小鹅身份映射**：`xiaoe_user_id` ↔ 可选的本平台 `user_id`，用于订单/学习数据关联 |
| `user_profiles` | business-039 | 画像扩展，含 `xiaoe_user_id`、`xiaoe_data` 等冗余字段 |
| `sys_user` | master | 本平台登录账号 |

### 2.2 为什么不能把采集用户塞进 `oauth_user`

1. **语义不对**：`oauth_user` 是「用户主动用第三方登录本站」的凭证表，需要 token/source；采集是**商家后台爬数同步**，没有 OAuth 授权流。  
2. **强制绑定**：`oauth_user.user_id` NOT NULL —— 一期明确**不自动建 `sys_user`**，大量小鹅用户无法插入。  
3. **缺号/延期无关**：oauth 表无「下次可查手机号」字段，硬塞会污染登录域。  
4. **source 枚举**：面向 AuthDefaultSource（GITHUB/QQ…），不是「小鹅通店铺用户列表」。

结论：`oauth_user` = 登录联邦；`xiaoe_user_mapping` = 小鹅业务身份。采集落库应落后者。

### 2.3 为什么不必再加 `xiaoe_user_phone_gap`

缺号队列需要的状态只有：

- 这个小鹅用户是谁（已有 `xiaoe_user_id` UK）  
- 当前有没有手机号  
- 下次允许再查的时间  

这些挂在 **`xiaoe_user_mapping` 扩展列**即可，`/umissing` 直接查本表：

```sql
-- 语义示意
WHERE (phone IS NULL OR phone = '')
  AND (phone_next_query_at IS NULL OR phone_next_query_at <= now())
  AND del_flag = 0
LIMIT :limit
```

**不加第二张表**的原因：一期简单、与「用户档案」同生命周期、避免 mapping 与 gap 双写一致性问题。

`user_profiles.xiaoe_*`：一期**不写**，避免双份快照；映射表已有 `json_data` 即可。

## 3. `xiaoe_user_mapping` 表扩展设计（拟 Liquibase）

在现有列基础上新增（名称可再定，语义如下）：

| 拟增列 | 类型建议 | 含义 |
| --- | --- | --- |
| `phone` | `VARCHAR(32)` | 采集到的手机号；空串/NULL=缺号 |
| `phone_next_query_at` | `TIMESTAMPTZ` | 缺号延期：下次允许被 `/umissing` 下发的时间；有号时可清空 |
| `nick_name` | `VARCHAR(255)` | 便于列表展示的昵称（来自 `user_name` 等） |
| `json_data` | `jsonb` | **每次上报覆盖**的该用户最新原始 list 项（或含 phones 合并视图，见下） |

现有保留：`user_id`（本平台，可空）、`xiaoe_user_id`（UK）、`mapping_type`、`confidence_score`、`mapped_time`、审计字段等。

索引建议：

- 保留 `uk(xiaoe_user_id)`  
- 新增部分查询友好索引：`(phone_next_query_at)` 或表达式索引视库型而定；至少普通 btree 可接受一期数据量  

### 3.1 用户上报落库算法（具体）

对 `payload.data.list[]` 每一项，`xeId = item.user_id`，`phone = payload.phones[xeId] ?? ""`：

```text
按 xiaoe_user_id 查 xiaoe_user_mapping
若 不存在:
    INSERT 新行（xiaoe_user_id, nick_name, phone, json_data=item最新, user_id=null, ...）
    若 phone 为空: phone_next_query_at = now()   // 立即可被 umissing 捞（或按产品改为 now+3d）
    若 phone 非空: phone_next_query_at = null
若 已存在:
    UPDATE nick_name、json_data=最新 item、update_time
    若 phone 非空:
        更新 phone；phone_next_query_at = null
        若 mapping.user_id 非空 且 sys_user.phonenumber 为空:
            回写 sys_user.phonenumber = phone
        若 sys_user.phonenumber 已有值: 不覆盖
    若 phone 为空:
        不清空已有 phone（避免一次空结果抹掉历史真号）——建议：仅当原 phone 已空时保持空，并设置 phone_next_query_at = now()+3天
```

空号延期规则（与下发一致）：

| 事件 | `phone_next_query_at` |
| --- | --- |
| 上报 phone 为空（且仍无有效号） | 标为 **当前时间 + 3 天** |
| 上报 phone 非空 | 置 `null`（不再进入 umissing） |
| `/umissing` 下发条件 | `phone` 空 **且**（`phone_next_query_at` 为空 **或** `<= now()`） |

> 说明：首次入库若立刻 `now()+3d`，则三天内不会进 umissing；若希望「首次可马上补查」，首次可 `null` 或 `now()`，仅在「查过仍空」时打 +3d。  
> **建议默认（待你确认）**：上报空号一律 `now()+3d`；首次入库空号同样 +3d（极低频，符合监视节奏）。若要首次可查，改为首次 `null`。

### 3.2 `json_data` 存什么

建议存**单用户维度**最新快照，例如：

```json
{
  "list_item": { /* 小鹅 list 原始一项 */ },
  "phone": "138...",
  "captured_at": "...",
  "batch_id": "..."
}
```

每次该用户再次上报 → **整列覆盖为最新**，不保留历史版本（一期简单）。

## 6. 处理流水线（拟）

```text
解密 report
  → source=order_list → upsert xiaoe_orders
  → source=user_list  → 遍历 list + phones → upsert xiaoe_user_mapping（§3.1）
                      → 不写 user_profiles
  → return { ok: true, ... }
```

`/umissing` → 只读 mapping → 返回 `userIds`。

## 8. 风险与建议

1. **FK**：现 `xiaoe_user_mapping.user_id` → `sys_user` ON DELETE CASCADE；`user_id` 可空时插入需确认库是否允许 NULL（设计已可空）。  
2. **空号不覆盖真号**：更新时 phone 为空不要把已有号清空。  
3. **金额分→元**。  
4. **隐私**：日志不打手机号。  
5. **oauth_user 勿混用**。  
6. 首次空号是 `null` 还是 `now()+3d`：见 §3.1，需你点一句。
