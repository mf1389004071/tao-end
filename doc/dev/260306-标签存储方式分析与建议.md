# 标签存储方式分析与建议

> 基于 `changelog-2-business.xml` 的现状分析，面向「基于标签的查询、过滤、统计」给出统一建议。  
> 文档位置：tao-end/doc/dev/

## 1. 现状：两种存储方式

### 1.1 存「标签值」（文本）

| 表 | 字段 | 类型 | 说明 |
|----|------|------|------|
| `knowledge_content` | `tags` | TEXT | 标签(逗号分隔)，如 "成长,领导力,读书" |
| `event_info` | `event_tags` | TEXT | 活动标签，自由文本 |
| `user_activity_logs` | `event_tags` | jsonb | 事件标签列表(JSON)，格式未在 changelog 中约定 |

特点：实现简单、无需维护标签主数据；适合「自由打标签、不要求统一词表」的展示场景。

### 1.2 存「标签 ID」（关联表）

| 表 | 说明 |
|----|------|
| `tags` (business-040) | 通用标签定义表：id, tag_type, code, name, parent_id, order_num 等 |
| `user_tags` (business-041) | 用户-标签多对多：user_id, **tag_id**, weight, source |

特点：标签统一维护、可重命名/合并、便于 JOIN 统计与推荐；用于用户画像等「体系化标签」场景。

---

## 2. 为什么会出现两种方式？

- **历史与场景差异**
  - 知识内容、活动设计时，可能优先考虑「录入简单、展示即用」，用单字段 TEXT 存标签值即可。
  - 用户画像需要「能力/兴趣/行业/资源」等统一词表、权重与来源，因此引入了 `tags` + `user_tags` 存 ID。
- **未统一规划**
  - 没有在全局约定：凡涉及「可查询、可统计」的标签，一律走 `tags` + 关联表。

---

## 3. 对「查询、过滤、统计」的影响

| 维度 | 存值 (TEXT/jsonb) | 存 ID (关联表) |
|------|--------------------|----------------|
| **按标签名查询** | LIKE/正则，难用索引，全表扫描 | 先查 tags 得 id，再 JOIN 关联表，可走索引 |
| **多标签 AND/OR 过滤** | 复杂且易出错 | 用 EXISTS/IN + 关联表，清晰可维护 |
| **按标签统计（如某标签下内容数）** | 需应用层或复杂 SQL 解析字符串 | GROUP BY tag_id / COUNT，简单 |
| **标签重命名/合并** | 需批量 UPDATE 多处文本 | 只改 tags 表一行 |
| **与用户画像标签联动** | 难以「同标签」打通内容与用户 | 同一 tag_id 可关联内容、活动、用户 |

结论：若后续要**基于标签做查询、过滤、统计**，存值方式会成为瓶颈；建议**统一以「标签 ID + 关联表」为主**。

---

## 4. 建议方案

### 4.1 原则

- **可查询、可过滤、可统计的标签**：一律通过 `tags` 表 + 「业务实体-标签」关联表存 **tag_id**，不存裸文本。
- **仅展示、不参与检索的补充信息**：可保留少量 TEXT（如「其他关键词」）作展示用，不作为统计与过滤依据。

### 4.2 知识内容 (knowledge_content)

- **现状**：`tags` TEXT 逗号分隔。
- **建议**：
  1. 新增关联表，例如 `knowledge_content_tags(content_id, tag_id)`，存 tag_id；可选唯一约束 (content_id, tag_id)。
  2. 查询/过滤/统计：JOIN `tags` 与 `knowledge_content_tags`，按 tag_id 或 tag_type/code/name 过滤。
  3. 原 `knowledge_content.tags` 可保留一段时间做兼容或仅作「展示用冗余」，新逻辑以关联表为准；待迁移与校验完成后，可弃用或仅写展示用。

### 4.3 活动 (event_info)

- **现状**：`event_tags` TEXT。
- **建议**：
  1. 新增关联表，例如 `event_info_tags(event_id, tag_id)`，存 tag_id。
  2. 按标签查活动、按活动统计标签分布：均通过 JOIN `tags` + `event_info_tags` 实现。
  3. 原 `event_info.event_tags` 同样可保留作兼容/展示，逐步迁移到关联表。

### 4.4 用户行为日志 (user_activity_logs)

- **现状**：`event_tags` jsonb，未约定结构。
- **建议**：
  - 若用于分析/统计：约定为「tag_id 数组」或 `[{ "tag_id": 1, "name": "xxx" }]`，以 tag_id 为主，便于与 `tags` 一致和统计。
  - 若仅作原始日志快照：可保留 jsonb，但统计时以「从业务表（内容/活动）的标签关联表」为准，不依赖日志内 event_tags。

### 4.5 用户画像 (user_tags)

- 已采用 **tag_id**，无需改动；与内容/活动统一使用 `tags` 后，可做「同一标签下的内容、活动、用户」统一分析。

### 4.6 标签主数据 (tags)

- 保持现有设计；如需区分「内容用」与「用户画像用」，可用 `tag_type`（如 CONTENT/EVENT/ABILITY/INTEREST 等）区分，便于过滤与扩展。

---

## 5. 实施顺序建议（MVP 内可按需裁剪）

1. **确定 tag_type 枚举**：在 `tags` 上约定内容/活动/用户等使用的 type，与现有 ABILITY/INTEREST 等一致或扩展。
2. **新增关联表**：`knowledge_content_tags`、`event_info_tags`，并补充 changelog。
3. **数据迁移**：将现有 `knowledge_content.tags`、`event_info.event_tags` 的文本解析后，匹配或创建 `tags` 记录，写入关联表。
4. **接口与查询**：列表/筛选/统计接口改为基于 tag_id 与关联表；必要时保留对旧字段的读兼容。
5. **弃用旧字段**（可选）：在确认无依赖后，将 `tags`/`event_tags` 改为仅展示或从表结构中移除。

---

## 6. 小结

| 问题 | 结论 |
|------|------|
| 为什么有的存值、有的存 ID？ | 历史与场景差异：简单展示用文本，用户画像用体系化标签（ID）。 |
| 建议？ | **统一以「tags 表 + 业务-标签关联表」存 tag_id**，便于查询、过滤、统计；内容与活动建议新增关联表并迁移。 |
| 后续查询/过滤/统计 | 以 tag_id 和关联表为主，避免对 TEXT 的 LIKE/正则；行为日志中的 event_tags 建议约定为 tag_id 或含 tag_id 的 JSON。 |

以上方案与现有 `tao-end/doc/dev` 及 changelog 中的表设计保持一致，扩展时需同步更新 260305-业务数据表设计与映射说明 等文档。
