# 时间类型与多时区架构评估

> **已按本方案完成改造**（数据库可重建场景）：BaseEntity/Listener/DateUtils、Liquibase 全量 TIMESTAMPTZ、业务实体时刻字段改为 Instant、查询条件 parseToInstant、代码生成器输出 Instant。详见本次提交与 `tao-end/doc/dev/` 下相关说明。

## 一、推荐映射与最佳实践（你的目标）

| PostgreSQL 类型 | Java 类型 | 说明 |
|-----------------|-----------|------|
| `timestamptz`   | `java.time.Instant` | 存 UTC，程序用 Instant，展示时转用户时区 |

**多时区推荐架构（最佳实践）：**

1. **数据库存 UTC**：所有“时刻”字段用 `timestamptz`，写入/读取均为 UTC。
2. **程序用 Instant**：业务层、实体类用 `Instant`，无歧义、易比较、易序列化。
3. **展示转用户时区**：接口返回 ISO-8601（如 `2025-03-07T12:00:00Z`）或时间戳，前端按用户时区格式化；或后端按用户时区转成字符串再返回。

---

## 二、当前项目是否按此实现？

**结论：目前没有。** 项目采用的是「无时区约定」的经典做法：

| 层级 | 当前实现 |
|------|----------|
| **数据库** | Liquibase 中全部为 `type="TIMESTAMP"`（无时区）。MySQL 下 TIMESTAMP 按会话时区；若迁 PostgreSQL，当前写法对应 `timestamp`（无时区），不是 `timestamptz`。 |
| **实体基类** | `BaseEntity` 的 `createTime`、`updateTime` 为 **`java.util.Date`**，`@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")`，无时区信息。 |
| **业务实体** | 如 `SysUser` 的 `loginDate`、`pwdUpdateDate` 为 `Date`；部分实体有 `LocalDate`（如 `SysDept.deleteTime`）；仅 `Message` 等极少数用 `Instant`。 |
| **自动填充** | `BaseEntityListener` 使用 `DateUtils.getNowDate()`（即 `new Date()`）设置创建/更新时间，依赖 JVM 默认时区。 |
| **工具类** | `DateUtils` 以 `Date`、`LocalDate`、`LocalDateTime` 为主，有少量 `ZoneId`/`ZonedDateTime` 与 Date 互转。 |

因此：**当前是「TIMESTAMP（无时区/会话时区）+ java.util.Date + 无统一 UTC/用户时区策略」，不是「timestamptz + Instant + 存 UTC、展示转用户时区」。**

## 三、若改为推荐架构，需改哪些地方？难度如何？

### 3.1 改动范围概览

| 类别 | 改动内容 | 难度 | 说明 |
|------|----------|------|------|
| **1. 数据库（Liquibase）** | 新表/新字段用 `timestamptz`；已有表若迁 PG 可逐步改为 `timestamptz` 并做数据迁移 | 中 | 新表简单；老表需约定现有数据时区再转 UTC |
| **2. BaseEntity + 基类监听** | `createTime`/`updateTime` 改为 `Instant`；监听器里用 `Instant.now()` | 小 | 集中改 1 个实体类 + 1 个监听器 |
| **3. 所有继承 BaseEntity 的实体** | 无额外改法：字段类型随 BaseEntity 变更即可 | 小 | 若子类自己又声明了 createTime/updateTime 需删掉或改为 Instant |
| **4. 业务实体中的“时刻”字段** | 将 `Date`/`LocalDateTime` 改为 `Instant`（仅“时刻”）；“日期”可保留 `LocalDate` | 中 | 散布在多个模块，需逐个排查 |
| **5. MyBatis-Flex / JDBC** | 确认 Instant ↔ timestamptz 映射（JDBC 4.2+ 与 PG 驱动支持）；必要时加 TypeHandler | 小～中 | 多数情况无需自定义 |
| **6. JSON 序列化** | Instant 默认 ISO-8601；若需固定格式可 `@JsonFormat` 或全局配置 | 小 | 前端能解析 ISO-8601 即可 |
| **7. 业务代码与查询** | `DateUtils.getNowDate()` → `Instant.now()`；查询条件中 `params.beginTime`/`endTime` 若为“用户时区”需转成 Instant 再查 | 中 | 涉及所有 setCreateTime/setUpdateTime、时间范围查询 |
| **8. 代码生成器** | GenConstants/GenUtils/domain 模板：时间类型生成 `Instant`，格式/导入相应调整 | 小 | 集中改 Generator 模块 |
| **9. 前端** | 接收 ISO-8601 或时间戳，按用户时区展示；筛选若传“日期”需与后端约定 | 小 | 通常已有日期库可处理 |

### 3.2 具体改动点（按依赖顺序）

1. **geek-common**
   - `BaseEntity`：`createTime`、`updateTime` 改为 `Instant`；`@JsonFormat` 可保留或改为 ISO-8601。
   - `DateUtils`：增加 `getNowInstant()`、`Instant` 与字符串/用户时区互转等，供逐步替换。

2. **geek-framework**
   - `BaseEntityListener`：`setCreateTime(Instant.now())`、`setUpdateTime(Instant.now())`。

3. **数据库**
   - **新表 / 新业务**：Liquibase 中时间列用 `TIMESTAMPTZ`（PostgreSQL）或与 DBA 约定等效类型；若暂用 MySQL，可仍用 TIMESTAMP 但约定“存 UTC”（应用层保证）。
   - **已有表迁 PG**：新增 changelog 将 `timestamp` 改为 `timestamptz`，并做一次数据迁移（把现有值按“约定时区”转成 UTC 写入）。

4. **MyBatis-Flex / 驱动**
   - 确认 PostgreSQL 驱动与 JDBC 4.2 对 `Instant` ↔ `timestamptz` 的读写无误；若有问题，为 `Instant` 写一个 TypeHandler 注册到 Flex。

5. **业务模块**
   - 所有直接使用 `Date` 的“时刻”字段（如 `SysUser.loginDate`、各业务 create_time/update_time 等）：类型改为 `Instant`，赋值改为 `Instant.now()` 或从接口/前端解析得到 Instant。
   - 查询条件：若前端传“用户时区的日期范围”，在 Service 层先转成 UTC 的 `Instant` 再传给 Mapper。

6. **代码生成器（Geek-Module-Generator）**
   - `GenConstants`：时间类型常量改为对应 `Instant`（或新增 TYPE_INSTANT）。
   - `GenUtils.initColumnField`：`datetime`/`timestamp`/`timestamptz` → 生成 `Instant`。
   - `GenColumn`：`getJavaTypeForField()`/`getDateFormatPattern()` 对时间类型返回 `Instant` 及合适格式（如 ISO-8601）。
   - `VelocityUtils.getImportList`：时间类型导入 `java.time.Instant`。
   - domain 模板：时间字段类型为 `Instant`，`@JsonFormat` 按需（ISO-8601 可省略）。

7. **前端（tao-pc / tao-app）**
   - 时间展示：用 dayjs/moment 等按用户时区解析接口返回的 ISO-8601 或时间戳。
   - 时间筛选：与后端约定传参格式（如传 UTC 起止或“用户时区日期 + 后端转 UTC”）。

## 四、难度与建议

- **整体难度：中等。** 概念清晰、改动点明确，但涉及基类、监听器、所有继承 BaseEntity 的实体、多处业务时间字段与查询、以及代码生成器，需要一次性或分阶段推进。
- **建议实施顺序**：
  1. 先做 **BaseEntity + BaseEntityListener + DateUtils 补充**，并确认 MyBatis-Flex/PostgreSQL 下 `Instant` 读写正常。
  2. 新业务、新表一律 **timestamptz + Instant**；老表可暂不动，或单独排期做“timestamp → timestamptz + 数据迁移”。
  3. 再逐步把业务实体中的“时刻”字段从 `Date` 迁为 `Instant`，并统一查询条件中的时区处理。
  4. 最后调整代码生成器，使新生成代码符合「timestamptz + Instant」与「存 UTC、展示转用户时区」的约定。

若你希望**仅在新模块采用 Instant + timestamptz**，而老代码暂时保留 Date + TIMESTAMP，也可以：只需在代码生成器与新建表/新实体上使用新规范，并在文档中约定“新表用 timestamptz + Instant，老表维持现状”，改动量会小很多。
