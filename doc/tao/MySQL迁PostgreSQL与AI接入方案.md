# MySQL 迁 PostgreSQL+pgvector 与 AI 接入方案

> 基于当前 tao-end（RuoYi-Geek）框架结构，说明：① 将底层数据库从 MySQL 换为 PostgreSQL+pgvector 的难度与改动量；② AI 如何按现有设计结构接入最符合、最简单。

---

## 一、MySQL → PostgreSQL+pgvector：难度与改动量

### 1.1 总体结论

| 维度 | 评估 |
|:---|:---|
| **难度** | **中等**。框架已具备 PostgreSQL 与多库支持，无需改核心架构，主要是配置、依赖、建表脚本与少量 SQL 差异。 |
| **改动量** | **小～中**。配置与依赖为集中改动；Liquibase 需适配 PG 或改用 PG 专用脚本；Mapper 已预留 PostgreSQL 分支。 |
| **风险** | 低。可先在本机/测试环境切 PG 验证，再决定是否废弃 MySQL。 |

---

### 1.2 已具备的 PG 支持（无需改代码）

当前项目**已经**为 PostgreSQL 做了部分准备，以下可直接复用：

- **数据源配置**：`application-data.yml` 中已有注释掉的 PostgreSQL 示例（url/username/driver），只需启用并填写实际连接信息。
- **MyBatis-Flex 方言**：`DataScopeDialectImpl` 中已有 `POSTGRE_SQL` 分支（双引号关键字、`LimitOffsetProcessor.POSTGRESQL`），Flex 会根据 **JDBC URL 自动识别** DbType，无需在代码里写死。
- **数据权限与工具类**：`DataScopeAspect`、`SqlUtil.findInSet` 等已按 `DbType.POSTGRE_SQL` 分支处理部门层级、find_in_set 等逻辑。
- **部分 Mapper**：`SysDictTypeMapper.xml`、`SysDictDataMapper.xml` 已使用 `_databaseId == 'postgresql'` 区分 `sysdate()` 与 `CURRENT_TIMESTAMP`。

因此：**只要把数据源改为 PostgreSQL，并补全“依赖 + 建表 + MyBatis databaseId”三块，即可跑通业务。**

---

### 1.3 需要做的改动清单

#### （1）依赖（pom.xml）

| 位置 | 操作 |
|:---|:---|
| **根 pom** | 在 `dependencyManagement` 中增加 PostgreSQL 驱动，与 MySQL 二选一或并存（按需保留 MySQL 用于多数据源）。 |
| **geek-admin/pom.xml** | 将 `mysql-connector-j` 改为或增加 `org.postgresql:postgresql`（如 42.7.x），scope 建议 `runtime`。 |

```xml
<!-- 示例：geek-admin/pom.xml 中替换或新增 -->
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
</dependency>
```

根 pom 的 `dependencyManagement` 中需声明版本，例如：

```xml
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <version>42.7.3</version>
</dependency>
```

**改动量**：2 处（根 pom + geek-admin）。

---

#### （2）配置文件

| 文件 | 修改内容 |
|:---|:---|
| **application-data.yml** | 将主数据源改为 PostgreSQL：`url: jdbc:postgresql://127.0.0.1:5432/ry`，`driver-class-name: org.postgresql.Driver`，`username/password` 按实际填写。 |
| **application.yml** | `pagehelper.helperDialect` 从 `mysql` 改为 `postgresql`。 |
| **liquibase.properties**（若仍用 Liquibase） | `driver`、`url` 改为 PostgreSQL。 |

**改动量**：2～3 处，集中且简单。

---

#### （3）建表与初始化（Liquibase / SQL）

当前 `changelog-1-master.xml` 使用了一些 **MySQL 特有** 写法：

- `type="datetime(0)"` → 在 PostgreSQL 中需为 `timestamp`（或带时区 `timestamptz`）。Liquibase 会按 DB 映射类型，但 `datetime(0)` 的 `(0)` 可能需去掉或改用通用类型。
- `autoIncrement="true"` → PostgreSQL 用 `SERIAL`/`BIGSERIAL` 或 `GENERATED BY DEFAULT AS IDENTITY`。

可选两种方式：

- **方案 A（推荐）**：为 PostgreSQL 单独做一套 Liquibase changelog（如 `db/changelog/changelog-1-pg.xml`），表结构用 PG 语法（BIGSERIAL、TIMESTAMP 等），数据可继续用 CSV 或从现有 MySQL 导出后导入。这样不改动原有 MySQL 的 changelog，PG 专用脚本维护成本低。
- **方案 B**：在现有 changelog 里为 PG 写 `dbms="postgresql"` 的 changeSet，或把 `datetime(0)` 改为 Liquibase 的通用类型（如 `TIMESTAMP`），由 Liquibase 按库生成对应 DDL。改动面稍大，需逐表核对。

**改动量**：方案 A 为新增 1 套 PG 建表/数据脚本（工作量约 1 天内的梳理+编写）；方案 B 为修改现有 changelog 并回归测试。

---

#### （4）MyBatis 的 databaseId（若用 XML 里的 _databaseId）

部分 Mapper 已用 `_databaseId == 'postgresql'`，要使其生效，需让 MyBatis 的 `SqlSessionFactory` 使用 `DatabaseIdProvider`。当前若依极客可能未显式配置，需要：

- 在**框架层**（如 `geek-framework` 的 config 包下）增加一个配置类：
  - 定义 `DatabaseIdProvider` Bean（例如 `VendorDatabaseIdProvider`）。
  - 将该 Bean 注入到 MyBatis-Flex 暴露的 `SqlSessionFactory`（或 Flex 使用的工厂）的 `setDatabaseIdProvider(...)`。
- 这样所有 XML 里 `_databaseId == 'postgresql'` 的分支会在连接 PG 时生效。

**改动量**：新增 1 个配置类 + 1 次注入，约 10～20 行代码。

---

#### （5）Mapper XML 中的 SQL

- **concat**：当前使用的 `concat('%', #{x}, '%')` 在 PostgreSQL 中**同样支持**，无需改。
- **sysdate() / CURRENT_TIMESTAMP**：仅 `SysDictTypeMapper`、`SysDictDataMapper` 两处，且已按 `_databaseId` 区分，配置好 databaseId 后即可。

**改动量**：0（仅依赖上面 databaseId 配置）。

---

#### （6）Druid 连接校验

`validationQuery: SELECT 1` 对 MySQL 和 PostgreSQL 都适用，无需改。

---

#### （7）pgvector 扩展（向量检索）

在 PostgreSQL 上启用向量能力：

1. **库内启用扩展**：在目标库执行 `CREATE EXTENSION IF NOT EXISTS vector;`（需安装 pgvector 扩展）。
2. **业务表**：新增“知识向量”等表，例如一列类型为 `vector(1536)`，用于存 embedding；其余业务表无需因“换 PG”而改结构。
3. **Java 端**：可用 JDBC 直接执行 `SELECT ... ORDER BY embedding <=> $1 LIMIT k`；或引入 `pgvector-java` 等类型支持，在实体中映射向量列。建议先做“最小接入”（单独一张向量表 + 一个 Mapper/Repository），再与业务（如 RAG）对接。

**改动量**：新增扩展 + 1～2 张表 + 少量 Java 代码，与“换库”本身可拆开做：先换 PG 跑通，再加 pgvector。

---

### 1.4 工作量汇总（经验值）

| 项 | 预估 |
|:---|:---|
| 依赖 + 配置 + PageHelper | 0.5 天 |
| PG 建表/数据脚本（方案 A）或 Liquibase 适配（方案 B） | 0.5～1 天 |
| DatabaseIdProvider 配置 | 0.5 天 |
| 联调、回归（登录/权限/字典/用户等） | 1～2 天 |
| **合计** | **约 2.5～4 天**（不含 pgvector 业务表与 RAG 逻辑） |
| 若再加 pgvector 扩展 + 一张向量表 + 简单查询接口 | +0.5～1 天 |

## 二、AI 接入：如何最符合当前框架且最简单

### 2.1 设计原则（对齐当前结构）

- **模块化**：与现有 **geek-modules**（如 generator、message、quartz）和 **geek-plugins**（如 Redis、MinIO）一致，AI 作为**可选能力**接入，不污染核心框架。
- **配置化**：开关、模型类型、API 地址、密钥等全部走 `application-*.yml`，便于环境切换与关闭。
- **单一职责**：框架层只提供“调用 AI 的能力”和可选“向量存储/检索”；业务语义（RAG、摘要、推荐）放在业务模块（如未来的知识库/内容模块）中。

这样既符合若依极客的“插件/模块可插拔”设计，又便于一人用 AI 辅助开发时边界清晰。

---

### 2.2 推荐形态：独立 AI 模块（geek-module-ai 或 geek-plugin-ai）

建议以 **geek-module-ai** 形式存在（与 flowable、message 等平级），便于在根 pom 与 geek-admin 的 pom 中按需引入。

**模块职责**：

- 定义 **AI 调用门面**（如 `AiRouterService` 或 `AiFacade`）：输入为“任务类型 + 文本/消息”，输出为“模型返回结果”。
- **路由策略**：按任务类型（摘要、问答、转写等）或配置选择后端（DeepSeek / OpenAI / 通义等），与需求文档中的“混合模型路由”一致。
- **不包含**具体业务（如“知识库 RAG”）：RAG 的组装（检索 + 拼 prompt + 调 AI）放在业务模块，本模块只提供“发请求、拿结果”和可选“向量检索接口”。

**与现有设计的关系**：

- 配置：在 `application-plugins.yml` 或新建 `application-ai.yml` 中写 `geek.ai.xxx`，与 Redis、MinIO 等同一风格。
- 依赖：仅需 HTTP 客户端（Spring 自带的 `RestTemplate` 或 `WebClient`）+ JSON 解析，无额外重量级依赖。
- 扩展：后续若要加“向量检索”，可在本模块内增加对 pgvector 的封装（或单独一个 small 的 vector 包），对外暴露“按向量查最近邻”的接口，仍由业务模块决定“查哪张表、拼什么 prompt”。

---

### 2.3 最小实现示例（保持简单）

下面给出“最符合当前框架、实现最简单”的一种做法。

**（1）模块结构（示意）**

```text
geek-module-ai/
├── pom.xml
└── src/main/java/com/geek/ai/
    ├── config/
    │   └── AiAutoConfiguration.java   // 开关、RestTemplate、Bean 注册
    ├── properties/
    │   └── AiProperties.java          // geek.ai.xxx 配置项
    ├── client/
    │   ├── AiClient.java              // 通用接口：chat(content, options)
    │   └── impl/
    │       ├── DeepSeekClient.java
    │       └── OpenAiCompatibleClient.java  // 兼容 OpenAI 协议，给 DeepSeek/部分国产用
    └── service/
        └── AiRouterService.java       // 根据任务类型选 client，调用并返回
```

**（2）配置（application-ai.yml 或 application-plugins.yml 片段）**

```yaml
geek:
  ai:
    enabled: true
    default-provider: deepseek
    providers:
      deepseek:
        base-url: https://api.deepseek.com
        api-key: ${DEEPSEEK_API_KEY:}
      openai:
        base-url: https://api.openai.com
        api-key: ${OPENAI_API_KEY:}
```

**（3）AiRouterService 使用方式（业务侧）**

```java
@Autowired
private AiRouterService aiRouterService;

// 业务模块中
String summary = aiRouterService.chat("summary", "请总结以下内容：\n" + longText);
```

这样业务层只依赖一个 `AiRouterService`，不关心具体是哪个模型、哪个 HTTP 调用，符合“简单、可插拔”的目标。

**（4）与 pgvector 的衔接（可选、后续做）**

- 在 **同一 PostgreSQL 实例** 上启用 pgvector，在业务库中建“知识向量表”。
- 在 **geek-module-ai** 中增加一层“向量检索”（如 `VectorSearchService`）：入参为 embedding 或文本（文本在服务内先调 embedding 接口再查），查 pgvector 表，返回 ID 或片段。
- RAG 流程：业务模块先调 `VectorSearchService` 拿到相关片段，拼成 prompt，再调 `AiRouterService.chat(...)`。这样 AI 模块仍只做“调用 + 向量检索”，业务模块做“RAG 编排”。

---

### 2.4 小结：AI 接入怎么最符合设计、最简单

- **最符合设计**：以 **geek-module-ai** 形式接入，与现有 module/plugin 风格一致；配置与开关集中、不侵入框架核心。
- **最简单**：先只做“一个配置类 + 一个 RouterService + 1～2 个 Client 实现（如 DeepSeek + OpenAI 兼容）”，业务通过 `AiRouterService` 调用；后续再在同一个模块内加“向量检索”和 pgvector，由业务模块做 RAG 编排。

---

## 三、实施顺序建议

1. **先换 PostgreSQL（不含 pgvector）**：改依赖、配置、PageHelper、PG 建表脚本、DatabaseIdProvider，跑通现有功能。
2. **再在 PG 上启用 pgvector**：建扩展、建向量表，在 AI 模块或单独小包中做“向量写入 + 最近邻查询”接口。
3. **最后加 geek-module-ai**：实现 AiRouterService + 1～2 个 Client，业务模块按需注入并调用；若要做 RAG，再在业务侧拼“向量检索 + prompt + AiRouterService”。

这样“底层换库”与“AI 能力”都贴合当前框架设计，改动集中、边界清晰，便于一人 + AI 协作开发。
